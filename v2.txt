# RAG Craft — Version 2 Development Prompt

Continue development of the existing RAG Craft Version 1 project.

DO NOT rebuild the project from scratch.

Version 1 already has the core RAG workflow working:

Create Chatbot
→ Upload Document
→ Extract Text
→ Chunk
→ Generate Embeddings
→ Store in Qdrant
→ Ask Question
→ Retrieve Knowledge
→ Generate Answer with Ollama
→ Display Source Citation

Version 2 should extend this foundation into a usable multi-user chatbot platform.

==================================================
1. IMPORTANT DEVELOPMENT RULES
==================================================

Before changing code:

1. Inspect the existing frontend and backend.
2. Understand the existing database models and migrations.
3. Understand the existing authentication implementation.
4. Understand the existing RAG pipeline.
5. Understand how chatbot/document isolation currently works.
6. Understand the existing conversation/message structure.
7. Reuse existing services, repositories, components, and utilities.
8. Do NOT duplicate existing functionality.
9. Do NOT rewrite working Version 1 features unnecessarily.
10. Preserve backward compatibility where practical.

Continue using:

Frontend:
- Next.js
- TypeScript
- Tailwind CSS
- App Router

Backend:
- Python
- FastAPI
- Pydantic
- SQLAlchemy
- Alembic

Data:
- PostgreSQL
- Qdrant

AI:
- Ollama
- llama3.2:3b
- nomic-embed-text

Architecture:

Next.js
   ↓
FastAPI
   ├── PostgreSQL
   ├── Qdrant
   └── Ollama

Frontend must never communicate directly with PostgreSQL or Qdrant.

Backend business logic should continue following:

API
→ Service
→ Repository

RAG logic should remain separated from normal application business logic.

==================================================
2. VERSION 2 MAIN GOAL
==================================================

Version 2 should allow real users to:

Register/Login
→ Create their own chatbot
→ Configure chatbot
→ Add knowledge
→ Test chatbot
→ Publish chatbot
→ Access chatbot through multiple channels
→ View conversations
→ View basic usage information

The platform has TWO authenticated roles:

ADMIN
USER

ADMIN represents the RAG Craft platform administrator/developer.

USER represents a customer using RAG Craft to create and manage their own AI chatbots.

External visitors using a Public Share Link, Web Widget, or Telegram Bot are NOT authenticated RAG Craft roles.

They are guests/channel users.

==================================================
4. USER OWNERSHIP AND DATA ISOLATION
==================================================

This is extremely important.

Every user-owned resource must have clear ownership.

A USER must only be able to manage their own:

- Chatbots
- Documents
- Knowledge sources
- Conversations
- Channel integrations
- Public links
- Web Widgets
- Telegram integrations

Do not trust owner_id/user_id received from frontend requests.

Determine the authenticated user from the authentication token/session.

Example:

Logged-in User A
→ Request Chatbot B
→ Backend checks ownership
→ If Chatbot B belongs to User B
→ Return 403 Forbidden

Continue enforcing chatbot knowledge isolation in Qdrant.

Retrieval must remain scoped to the correct:

organization_id
chatbot_id

Do not perform global retrieval.

11. MULTI-CHANNEL ACCESS
==================================================

Version 2 must implement THREE external access methods:

1. Telegram Bot
2. Web Widget
3. Public Share Link

All channels must reuse the SAME chatbot and SAME RAG pipeline.

Do NOT create separate RAG logic for each channel.

Concept:

Telegram ──────┐
Web Widget ────┼→ Chat Service → RAG Pipeline → Answer
Public Link ───┘

Create a reusable application-level chat service that channel adapters can call.

==================================================
12. TELEGRAM BOT INTEGRATION
==================================================

USER flow:

Select Chatbot
→ Open Telegram Integration
→ Enter Telegram Bot Token
→ Connect
→ Test Connection
→ Enable Integration

USER obtains the Bot Token from Telegram BotFather.

Backend should:

1. Validate the Bot Token using Telegram Bot API.
2. Create Telegram integration record.
3. Associate integration with:
   - owner/user
   - chatbot
4. Register the Telegram webhook.
5. Receive Telegram updates through FastAPI webhook endpoint.
6. Identify integration/chatbot.
7. Send incoming text to the shared chat/RAG service.
8. Send generated answer back through Telegram Bot API.

Conceptual endpoint:

POST /api/webhooks/telegram/{integration_identifier}

Do NOT expose internal sequential IDs unnecessarily.

Store Telegram Bot Tokens securely.

Never:

- Log Bot Token
- Return full Bot Token to frontend after storage
- Include Bot Token in URLs

USER can:

- View connection status
- Test connection
- Enable/disable integration
- Disconnect integration

Suggested statuses:

CONNECTED
DISCONNECTED
FAILED

==================================================
13. WEB WIDGET
==================================================

USER flow:

Select Chatbot
→ Generate Web Widget
→ System creates Widget ID/Public Key
→ Generate Embed Code
→ Copy Embed Code
→ Paste into Website

Example concept:

<script
  src="https://YOUR_DOMAIN/widget.js"
  data-widget-id="PUBLIC_WIDGET_ID">
</script>

Do NOT expose database IDs or secret API keys in public embed code.

Create a random public widget identifier.

Backend stores mapping:

widget_public_id
→ chatbot_id
→ owner_id

When website visitor opens widget:

Widget
→ Public Widget API
→ Validate Widget ID
→ Find Chatbot
→ Shared Chat Service
→ RAG
→ Response

USER can:

- Generate widget
- Copy embed code
- Enable widget
- Disable widget
- Regenerate public widget identifier if necessary

Use iframe isolation if appropriate so RAG Craft CSS does not conflict with the host website.

Keep Version 2 widget UI simple:

- Floating chat button
- Chat window
- Chatbot name
- Messages
- Starter questions
- Input
- Send button
- Loading state
- Error state

Do NOT build a complex visual widget designer yet.

==================================================

USER flow:

→ Generate Public Link
→ System generates secure random public token
→ Save token mapping
→ Display shareable URL

Example:

https://YOUR_DOMAIN/share/{public_token}

Do NOT expose:

/share/{chatbot_database_id}

Use a secure random public token.

Backend mapping:

public_token
→ chatbot_id
→ owner_id

Public visitor can:

- Open link without RAG Craft login
- View chatbot name
- View starter questions
- Ask question
- Receive answer
- View citations where allowed

Public visitor CANNOT:

- Edit chatbot
- Upload documents
- Change settings
- View dashboard
- View owner's private data

USER can:

- Generate link
- Copy link
- Enable/disable link
- Regenerate link

When regenerated:

Old token must stop working.

15. CHANNEL ARCHITECTURE
==================================================

Avoid duplicated chat/RAG code.

Create a shared abstraction similar to:

Channel Request
      ↓
Chat Service
      ↓
Validate Chatbot
      ↓
Create/Load Conversation
      ↓
RAG Pipeline
      ↓
Save Messages
      ↓
Return Response

Channel-specific code should mainly handle:

Telegram:
Telegram request/response conversion

Web Widget:
Widget request/session handling

Public Link:
Public token/session handling

The RAG pipeline itself should not care whether the question came from Telegram, Widget, Playground, or Public Link.

==================================================
21. API SECURITY
==================================================

Separate authenticated and public endpoints clearly.

Example:

/api/users/...
/api/chatbots/...
/api/admin/...

versus:

/api/public/share/...
/api/public/widget/...
/api/webhooks/telegram/...

Authenticated routes must verify current user.

Admin routes must verify ADMIN role.

Public endpoints must validate their public token/identifier.

Never rely only on frontend authorization.

- Telegram Bot Tokens
- JWT secret

==================================================
31. CODE QUALITY
==================================================

Follow best practices but keep the project understandable for a student development team.

Prioritize:

- Security
- Clear ownership
- Data isolation
- Modularity
- Maintainability
- Testability
- Reuse

Avoid:

- Giant service files
- Giant React components
- Duplicated channel logic
- Hard-coded URLs
- Hard-coded model names
- Hard-coded secrets
- Business logic inside API routes
- Database calls scattered through frontend
- Separate RAG implementations for each channel
- Premature microservices
- Premature optimization
- Unnecessary abstraction

Prefer simple, explicit code over overly clever architecture.
