# RAG Craft — Version 1 Development Prompt

Build **Version 1 of RAG Craft**, a Retrieval-Augmented Generation (RAG) platform.

Version 1 is a working prototype used to validate the core architecture before the full production system is developed by a team.

The main goal is to prove this workflow:

Admin Login  
→ Create Chatbot  
→ Upload Knowledge  
→ Process Document  
→ Generate Embeddings  
→ Store Vectors  
→ Ask Question  
→ Retrieve Relevant Knowledge  
→ Generate Answer  
→ Display Source Citation

Do NOT implement every planned RAG Craft feature yet.

Focus on making this core workflow reliable, understandable, modular, and easy to extend in Version 2 and Version 3.

---

# 1. Technology Stack

Use the following technologies.

## Frontend

- Next.js
- TypeScript
- Tailwind CSS
- App Router

## Backend

- Python
- FastAPI
- Pydantic
- SQLAlchemy
- Alembic

## Application Database

Use PostgreSQL.

For Version 1:

PostgreSQL runs using Docker.

The application must connect using environment variables such as:

DATABASE_URL

Do not hard-code database host, username, password, database name, or port.

The architecture must allow PostgreSQL Docker to later be replaced with a real PostgreSQL server without changing application business logic.

## Vector Database

Use Qdrant.

For Version 1:

Qdrant runs using Docker.

Qdrant is responsible for:

- Embedding vectors
- Vector similarity search
- RAG retrieval

PostgreSQL remains the source of truth for application/business data.

## LLM

Use Ollama.

Generation model:

llama3.2:3b

The generation model must be configurable through environment variables.

Example:

OLLAMA_MODEL=llama3.2:3b

## Embedding Model

Use a dedicated embedding model.

Recommended for V1:

nomic-embed-text

Do NOT use llama3.2:3b as the embedding model.

The embedding model should also be configurable.

Example:

EMBEDDING_MODEL=nomic-embed-text

# 5. Database Design

Prepare PostgreSQL so that Version 1 remains simple but can later support the production multi-tenant architecture.

Create these tables:

1. users
2. organizations
3. organization_members
4. chatbots
5. chatbot_settings
6. knowledge_sources
7. documents
8. document_chunks
9. conversations
10. messages
11. message_sources
12. ingestion_jobs
13. api_keys
14. audit_logs

Not every table needs a full UI in Version 1.

The purpose is to establish a clean normalized foundation.

Use:

- UUID primary keys where appropriate
- created_at
- updated_at
- foreign keys
- indexes
- unique constraints where necessary

Do not use unnecessary duplicated fields.

Use database migrations through Alembic.

# 9. Chatbot Isolation

This requirement is extremely important.

Every chatbot must have its own isolated knowledge.

Example:

Organization A

HR Assistant
→ HR Handbook
→ Leave Policy

IT Assistant
→ Network Guide
→ Troubleshooting Guide

When HR Assistant retrieves information, it must NEVER retrieve IT Assistant documents.

Every retrieval must be scoped by at least:

organization_id
chatbot_id

Do not perform a global vector search and filter the result afterward.

Filtering must happen during retrieval.

# 19. Qdrant

Run Qdrant through Docker.

Use Qdrant for vector storage and similarity search.

Each vector payload should contain enough metadata to enforce isolation.

Example conceptual payload:

{
    "organization_id": "...",
    "chatbot_id": "...",
    "document_id": "...",
    "chunk_id": "...",
    "document_name": "...",
    "page_number": 5,
    "chunk_index": 12
}

Use Qdrant payload filtering during search.

Search must include:

organization_id
AND
chatbot_id

Do not rely only on client-side filtering.

Keep responsibilities clear.

PostgreSQL stores application data:

- Users
- Organizations
- Membership
- Chatbots
- Settings
- Knowledge sources
- Documents
- Chunk metadata
- Conversations
- Messages
- Citations
- Jobs
- Audit information

Qdrant stores data required for vector retrieval:

- Vector
- chunk_id
- chatbot_id
- organization_id
- document_id
- retrieval metadata

PostgreSQL remains the main application source of truth.

# 21. RAG Retrieval Pipeline

When a question is submitted:

User Question
↓
Validate Chatbot Access
↓
Generate Query Embedding
↓
Search Qdrant
↓
Filter by organization_id + chatbot_id
↓
Retrieve Top-K Chunks
↓
Build Context
↓
Build Prompt
↓
Send to Ollama
↓
llama3.2:3b
↓
Generate Answer
↓
Return Answer + Sources

Top-K should be configurable.

Example:

TOP_K=5

# 41. Version 1 Acceptance Scenario

Version 1 is successful when this complete scenario works.

1. Start PostgreSQL.
2. Start Qdrant.
3. Start Ollama.
4. Start FastAPI.
5. Start Next.js.
6. Login as admin.
7. Create a chatbot called "HR Assistant".
8. Open its Knowledge Base.
9. Upload `employee-handbook.pdf`.
10. Document status becomes QUEUED.
11. Processing begins.
12. Status becomes PROCESSING.
13. Text is extracted.
14. Text is chunked.
15. Embeddings are generated.
16. Vectors are stored in Qdrant.
17. Status becomes READY.
18. Open Playground.
19. Ask a question whose answer exists in the document.
20. Query embedding is generated.
21. Qdrant retrieves relevant chunks belonging only to HR Assistant.
22. Retrieved context is sent to llama3.2:3b.
23. The model generates a grounded answer.
24. Frontend displays the answer.
25. Frontend displays the source document and page.
26. Create another chatbot.
27. Verify that the second chatbot cannot access HR Assistant's knowledge.

Only after this workflow is reliable should Version 2 development begin.

# 43. Code Quality Requirements

Keep the code understandable for a student development team.

Do not over-engineer the prototype.

Use clear naming.

Avoid giant files.

Avoid duplicated logic.

Add comments only where they explain important or non-obvious logic.

Use services and repositories where they provide clear separation.

Do not create unnecessary abstraction layers.

Use async code where it provides a real benefit, not simply everywhere.

Use proper database transactions where necessary.

Validate API input using Pydantic.

Use TypeScript types properly on the frontend.

Do not use `any` unnecessarily.

RAG Craft Version 1 is NOT intended to be the complete production platform.

It is intended to validate the foundation that the production system will build upon.

The most important architecture is:

Next.js
↓
FastAPI
↓
PostgreSQL + Qdrant
↓
RAG Pipeline
↓
Ollama llama3.2:3b

And the most important business flow is:

Create Chatbot
↓
Add Knowledge
↓
Process Knowledge
↓
Index Knowledge
↓
Ask Question
↓
Retrieve Correct Knowledge
↓
Generate Grounded Answer
↓
Show Citation

Prioritize correctness, knowledge isolation, modularity, and testability over adding more features.
